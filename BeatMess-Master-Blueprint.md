# BeatMess — Master Implementation Blueprint
### Principal Architect Handoff Document for Antigravity

> **A note before you start (read this once, then build):**
> `saavn.dev`-style APIs and the Piped/Invidious fallback both work by scraping/re-serving JioSaavn's and YouTube's content outside their official developer programs, without a license to redistribute the audio. That's fine for a private, single-user hobby build you run for yourself (this is a very common "learn full-stack dev" project pattern), but it's on legally shaky ground the moment it's distributed publicly, monetized, or scaled beyond you. Practical implications for this blueprint:
> - Keep the APK side-loaded / personal-use only. Don't publish it to the Play Store or a public download page.
> - Don't put your Firebase project on a public "sign up here" landing page — treat auth as access control for you (and maybe a few friends), not a public product.
> - Unofficial APIs like this go down or change shape without notice (several instances have died to rate-limits or takedown requests over the years) — the architecture below treats the music API as a **swappable adapter**, not a hardcoded dependency, specifically so you can survive that.
>
> With that said — here's the full engineering plan.

---

## 0. Guiding Architecture Principles

1. **Adapter pattern for music sources.** Every screen talks to a `MusicProvider` interface, never directly to `saavn.dev` or Piped. This means swapping/adding a third source later is a one-file change.
2. **Thin client, no custom backend server.** Firebase Client SDK only — no Node/Express layer to host. Keeps this 100% free (Firebase free tier + Vercel/Netlify free tier if you ever want a web build).
3. **Offline-tolerant state.** Zustand + Firestore's built-in offline persistence so the app doesn't break on flaky mobile data.
4. **Single audio engine, many sources.** One `HTMLAudioElement`-based player core; source URLs get swapped into it regardless of whether they came from JioSaavn or the YouTube fallback.
5. **Mobile-first player.** Capacitor Media Session + a foreground service config so audio survives screen-lock/backgrounding — this is the single trickiest part of the whole build, called out explicitly in Phase 8.

## 4. Firebase Firestore Schema Design

**Auth:** Firebase Auth (Email/Password + optionally Google provider). `uid` is the join key everywhere below.

```
users/{uid}
  ├── displayName: string
  ├── email: string
  ├── photoURL: string | null
  ├── createdAt: Timestamp
  └── preferences: {
        theme: "dark",
        streamQuality: "high" | "medium" | "data-saver",
        fallbackEnabled: boolean        // user toggle for YouTube fallback
      }

users/{uid}/likedSongs/{songId}
  ├── songId: string                    # provider-namespaced, e.g. "saavn:xyz123" or "yt:abc456"
  ├── title: string
  ├── artist: string
  ├── albumArtUrl: string
  ├── durationSec: number
  ├── source: "saavn" | "piped" | "invidious"
  └── likedAt: Timestamp

playlists/{playlistId}
  ├── ownerId: string                   # uid
  ├── title: string
  ├── description: string | null
  ├── coverImageUrl: string | null      # first song's art, or user-uploaded
  ├── isPublic: boolean                 # future-proofing; MVP = always false
  ├── createdAt: Timestamp
  └── updatedAt: Timestamp

playlists/{playlistId}/songs/{songId}
  ├── songId: string
  ├── title: string
  ├── artist: string
  ├── albumArtUrl: string
  ├── durationSec: number
  ├── source: "saavn" | "piped" | "invidious"
  ├── addedAt: Timestamp
  └── order: number                     # for manual reordering

users/{uid}/history/{historyEntryId}
  ├── songId: string
  ├── title: string
  ├── artist: string
  ├── albumArtUrl: string
  ├── source: "saavn" | "piped" | "invidious"
  ├── playedAt: Timestamp
  └── completed: boolean                # did they listen to >80%? (nice-to-have for "recommended")

users/{uid}/searchHistory/{entryId}
  ├── query: string
  └── searchedAt: Timestamp
```

**Indexes needed:** composite index on `history` (`uid` + `playedAt desc`) and on `playlists` (`ownerId` + `updatedAt desc`) — Firestore will prompt you with the exact console link the first time each query runs; just click "create index."

**Security rules (essential — write these in Phase 2, don't skip):**
```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
      match /{subcollection=**} {
        allow read, write: if request.auth != null && request.auth.uid == uid;
      }
    }
    match /playlists/{playlistId} {
      allow read, write: if request.auth != null && request.auth.uid == resource.data.ownerId;
      allow create: if request.auth != null && request.auth.uid == request.resource.data.ownerId;
      match /songs/{songId} {
        allow read, write: if request.auth != null &&
          request.auth.uid == get(/databases/$(database)/documents/playlists/$(playlistId)).data.ownerId;
      }
    }
  }
}
```

## 5. Music API Layer

### 5a. Primary engine — `saavn.dev`

The public instance is built on the `sumitkolhe/jiosaavn-api` project. Endpoint *paths* on these community-run unofficial wrappers do shift between versions, so **Phase 3, Step 1 for Antigravity is: hit `https://saavn.dev/docs` (or whatever live docs page the deployed instance exposes) and confirm the paths below before wiring `saavnProvider.ts`.** As of the current widely-deployed version, the shape is:

| Purpose | Endpoint |
|---|---|
| Global search (songs+albums+artists+playlists) | `GET /api/search?query={q}` |
| Search songs only | `GET /api/search/songs?query={q}&page=0&limit=20` |
| Search albums | `GET /api/search/albums?query={q}` |
| Search artists | `GET /api/search/artists?query={q}` |
| Search playlists | `GET /api/search/playlists?query={q}` |
| Get song by ID | `GET /api/songs/{id}` |
| Get song by JioSaavn link | `GET /api/songs?link={jiosaavnUrl}` |
| Song suggestions (for "Home" / autoplay queue) | `GET /api/songs/{id}/suggestions` |
| Song lyrics | `GET /api/songs/{id}/lyrics` |
| Get album | `GET /api/albums?id={id}` or `?link={url}` |
| Get playlist | `GET /api/playlists?id={id}` or `?link={url}` |
| Get artist | `GET /api/artists/{id}` |
| Artist's songs | `GET /api/artists/{id}/songs` |

**Response shape notes for `saavnProvider.ts`:**
- Song objects return a `downloadUrl` (or `download_url` depending on version) array with multiple bitrates (12kbps → 320kbps) — pick the highest for "high" quality setting, a mid one for "data-saver."
- Album art (`image`) is also an array of resolutions — grab the largest for the full-screen player, a smaller one for list rows (don't ship a 500x500 image into a 40px row thumbnail).
- Lyrics: some tracks return `lyrics` as plain text with no timestamps, others (fewer) return a synced/LRC-like structure. `useSyncedLyrics` must gracefully fall back to "auto-scroll estimate" when no timestamps exist (interpolate scroll position from song progress % against line count).

### 5b. Fallback engine — YouTube via Piped / Invidious

`pipedProvider.ts` implements the same `MusicProvider` interface:

| Purpose | Endpoint (Piped, instance-dependent — pick a public instance like `pipedapi.kavin.rocks` or self-host later) |
|---|---|
| Search | `GET {pipedInstance}/search?q={q}&filter=music_songs` |
| Video/stream info (gives direct audio-only stream URLs) | `GET {pipedInstance}/streams/{videoId}` |

- From `/streams/{videoId}`, pick the `audioStreams` array, filter for the highest-bitrate `audio/mp4` or `audio/webm` entry — that URL goes straight into the `<audio>` element.
- Invidious (`invidiousProvider.ts`) mirrors this with `GET {invidiousInstance}/api/v1/search?q={q}` and `GET {invidiousInstance}/api/v1/videos/{id}` (its `adaptiveFormats` array is the audio-source equivalent).
- **Keep a small hardcoded list of 2-3 fallback instance URLs** for each (public Piped/Invidious instances rotate and occasionally go offline) and have `musicGateway.ts` round-robin/retry across them before giving up.

### 5c. `musicGateway.ts` — the orchestration logic

```
search(query):
  1. results = await saavnProvider.search(query)
  2. if results.length > 0 → return { source: "saavn", results }
  3. else → results = await pipedProvider.search(query)
  4. if results.length > 0 → return { source: "piped", results }
  5. else → results = await invidiousProvider.search(query)
  6. return { source: "invidious", results } (or empty state)

getStreamUrl(song):
  - if song.source === "saavn" → return saavnProvider.getStreamUrl(song.id)
  - if that resolves to null/expired → fall through to pipedProvider.search(song.title + " " + song.artist), take best match, stream from there
  - same fallback chain for piped → invidious
```

Also give the user an explicit manual override — a "Try alternate source" button on the mini-player for cases where a JioSaavn match is the wrong version of a song (e.g., a cover instead of the original) and they specifically want the YouTube fallback triggered on demand, per your spec.

## 6. State Management Architecture

**`playerStore.ts` (Zustand)** — the single source of truth the whole player UI subscribes to:
```ts
interface PlayerState {
  queue: Song[];
  currentIndex: number;
  isPlaying: boolean;
  progressSec: number;
  durationSec: number;
  volume: number;           // 0–1
  isShuffled: boolean;
  repeatMode: "off" | "all" | "one";
  isFullScreenOpen: boolean;
  activeSource: "saavn" | "piped" | "invidious";

  playSong: (song: Song, queue?: Song[]) => Promise<void>;
  togglePlay: () => void;
  next: () => void;
  previous: () => void;
  seek: (sec: number) => void;
  setVolume: (v: number) => void;
  toggleShuffle: () => void;
  cycleRepeatMode: () => void;
}
```
`useAudioEngine.ts` subscribes to `playerStore` and is the *only* place that touches the actual `<audio>` element / native media bridge — never call `audioElement.play()` from a component; always go through the store action so state and playback can't drift apart.

**TanStack Query** handles all `musicGateway` calls (search, suggestions, lyrics) — gives you caching, retry, and loading/error states for free, keyed like `["search", query]`, `["song", id]`, `["lyrics", id]`.

**`authStore.ts`** mirrors Firebase Auth's `onAuthStateChanged` listener into Zustand so components don't each subscribe individually.

## 7. Step-by-Step Build Order for Antigravity

Work through these phases **in order** — each assumes the previous is done and running.

### Phase 0 — Project bootstrap
1. `npm create vite@latest beatmess -- --template react-ts`, cd in, `npm install`.
2. Install every package from Section 3.
3. Set up Tailwind config with the glassmorphism design tokens (see Section 9) in `tailwind.config.ts` and `globals.css`.
4. Set up absolute imports (`@/` → `src/`) in `tsconfig.json` and `vite.config.ts`.
5. Scaffold the empty folder structure from Section 2 with placeholder `index.ts` files.
6. Commit: "chore: project scaffold."

### Phase 1 — Firebase configuration
1. Create Firebase project in console (manual step — Antigravity should prompt the user for the config values, or read them from a `.env.local` the user has pasted in).
2. Enable **Authentication → Email/Password** (and Google if desired).
3. Create **Firestore Database** in production mode, nearest region.
4. Write `src/config/firebase.ts` initializing `initializeApp`, exporting `auth` and `db`.
5. Enable Firestore offline persistence (`enableIndexedDbPersistence(db)`).
6. Deploy the security rules from Section 4 via `firebase deploy --only firestore:rules` (requires `firebase init` + Firebase CLI logged in).
7. Build `authService.ts`: `signUp`, `signIn`, `signOut`, `onAuthChange`.
8. Build `LoginPage.tsx` / `RegisterPage.tsx` with the glass-card auth form.
9. Wire `authStore.ts` to Firebase's listener; add a route guard that redirects unauthenticated users to `/login`.

### Phase 2 — Music API service layer
1. Define `MusicProvider` interface and shared `Song`/`Album`/`Playlist`/`Artist` types in `types/`.
2. Build `saavnProvider.ts` against the confirmed endpoints from Section 5a. Normalize its raw response into the shared `Song` type immediately at the adapter boundary — nothing downstream should ever see raw JioSaavn JSON shape.
3. Build `pipedProvider.ts` and `invidiousProvider.ts` similarly, normalizing to the same `Song` type.
4. Build `musicGateway.ts` implementing the fallback chain from Section 5c.
5. Wrap all three providers' calls in TanStack Query hooks: `useSearch(query)`, `useSongSuggestions(id)`, `useLyrics(id)`.
6. Smoke test in a throwaway `/debug` route: search a query, log results, confirm fallback triggers when you deliberately search garbage text.

### Phase 3 — State management
1. Build `playerStore.ts` per Section 6 (logic only, no audio element yet — stub the play/pause actions).
2. Build `uiStore.ts` (active tab, full-screen player toggle, toast queue).
3. Build `lyricsStore.ts` (current line index, synced vs. estimated mode).

### Phase 4 — Audio engine (core player logic)
1. Build `useAudioEngine.ts`: owns a single `<audio>` ref, exposes imperative `play(url)`, `pause()`, `seek(sec)`, `setVolume(v)`; listens to `timeupdate`, `ended`, `error` events and pushes them into `playerStore`.
2. On `ended`: respect `repeatMode` — "one" replays same track, "all"/"off" advances via `next()` (which itself respects `isShuffled`).
3. Wire `playSong(song)` in the store to: (a) resolve a stream URL via `musicGateway.getStreamUrl(song)`, (b) call `useAudioEngine.play(url)`, (c) write a `history` entry via `historyService`.
4. Handle stream URL failures gracefully — if `saavn` URL 403s/expires mid-playback, auto-retry once through the fallback chain before surfacing an error toast.

### Phase 5 — Player UI components
1. `SeekBar.tsx` — controlled by `progressSec`/`durationSec` from the store, draggable, calls `seek()` on release (not on every drag-move, to avoid audio stutter).
2. `PlayerControls.tsx` — play/pause/skip/shuffle/repeat icons wired to store actions.
3. `VolumeSlider.tsx`.
4. `MiniPlayerBar.tsx` — fixed bottom, glassmorphism panel (Section 9), tapping it opens `FullScreenPlayer`.
5. `FullScreenPlayer.tsx` — large album art, gradient background derived/sampled from the art (or a static gradient token if you skip dynamic color extraction for MVP), controls, and a toggle to reveal `LyricsPanel`.
6. `LyricsPanel.tsx` — consumes `useSyncedLyrics(songId, progressSec)`; auto-scrolls active line into view, dims past/future lines.

### Phase 6 — Page layouts
1. `AppShell.tsx` + `BottomNav.tsx` (Home / Search / Library / Settings) + persistent `MiniPlayerBar` above the nav.
2. `HomePage.tsx` — trending/recommended rail(s) pulled from `saavnProvider` trending endpoint (or a curated "seed" search like `/api/search/songs?query=trending` if no dedicated trending endpoint exists on the deployed instance — verify during Phase 2).
3. `SearchPage.tsx` — `SearchBar` with `useDebouncedSearch` (300ms), results list grouped by songs/albums/artists.
4. `LibraryPage.tsx` — tabs for Liked Songs / Playlists / History, each backed by the corresponding Firestore service + a live `onSnapshot` listener for real-time updates across devices.
5. `PlaylistDetailPage.tsx` / `ArtistPage.tsx`.
6. `SettingsPage.tsx` — account info, stream-quality preference, and the **Force Refresh & Clear Cache** button (see Section 8).

### Phase 7 — Firestore integration wiring
1. `likedSongsService.ts`: `toggleLike(song)`, `useLikedSongs()` (live listener).
2. `playlistService.ts`: `createPlaylist`, `addSongToPlaylist`, `removeSongFromPlaylist`, `reorderSongs`, `deletePlaylist`.
3. `historyService.ts`: `logPlay(song)` (called from Phase 4 step 3), `useHistory(limit=50)`.
4. Wire `SongContextMenu.tsx` (long-press / kebab menu on any song row) to like-toggle and "add to playlist" modal.

### Phase 8 — Mobile: Capacitor + background audio (the hard part)
1. `npm install @capacitor/core @capacitor/cli @capacitor/android`, `npx cap init BeatMess com.yourname.beatmess`.
2. `npm run build` → `npx cap add android` → `npx cap sync`.
3. **Background audio**: web `<audio>` elements get suspended when Android backgrounds/locks the WebView. Two viable approaches, in order of recommendation:
   - **(a) `@capacitor-community/media`** or a similarly-scoped foreground-service audio plugin — bridges playback to a native Android `MediaSessionService` + persistent notification, so the OS treats it as a real media session (lock-screen controls, doesn't get killed).
   - **(b) If no existing plugin fits**, hand-write a minimal native Capacitor plugin: an Android `Service` with `MediaSessionCompat`, started/stopped from `useAudioEngine.ts` via `Capacitor.Plugins.BackgroundAudio.play(url)`. This is more work but gives full control — flag this to the user as a "if step (a) doesn't work reliably, escalate to option (b)" decision point rather than building it speculatively.
4. Wire `useMediaSession.ts` either way: expose play/pause/next/previous to Android's lock-screen media controls and the notification shade.
5. Add required Android manifest permissions: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK` (Android 14+ requires the specific type), `WAKE_LOCK`, `INTERNET`.
6. `npx cap sync android` after every native change.
7. Build debug APK: `cd android && ./gradlew assembleDebug` → output at `android/app/build/outputs/apk/debug/app-debug.apk`. Sideload via `adb install` or transfer directly to the device.

### Phase 9 — Settings: cache management
1. `cacheManager.ts`: clears TanStack Query cache (`queryClient.clear()`), clears `@capacitor/preferences` local KV store, and optionally clears the browser/WebView HTTP cache for audio blobs.
2. `SettingsPage.tsx` "Force Refresh & Clear Cache" button calls this, shows a confirming toast, and triggers a soft app reload (`window.location.reload()` on web / `App.reload` via Capacitor App plugin on native).

### Phase 10 — Polish pass
1. Add `LoadingSkeleton.tsx` states everywhere a network call is in flight (song rows, search results, playlist grids).
2. Add `ErrorState.tsx` for failed API calls with a manual retry button — and specifically test the "saavn down → falls back to Piped → falls back to Invidious → all down → clear error state" full chain.
3. Framer Motion: page-transition fades, mini-player slide-up-on-play, full-screen player spring-open.
4. Test the complete offline → online → offline cycle (Firestore should keep working from cache; audio playback obviously can't without network — surface that clearly rather than silently failing).
5. Final `npx cap sync android` + `./gradlew assembleDebug` for a release-candidate debug build.

## 8. Settings — "Force Refresh & Clear Cache" (detail)

This should clear, in order:
1. TanStack Query's in-memory + persisted cache (search results, song metadata, lyrics).
2. `@capacitor/preferences` keys (last-played state, cached stream-quality preference, any locally cached "trending" fallback data).
3. Optionally: unregister/re-register any service worker if you later add PWA support for the web build.
4. End with a toast ("Cache cleared") and a soft reload so the user sees a visibly fresh Home tab — this is as much a trust-building UX signal as it is a technical fix for stale API responses.

## 9. UI Design System — "Stitch-inspired" Dark Glassmorphism

Drop these into `globals.css` as the base tokens Antigravity should reuse everywhere rather than inventing new colors per-component:

```css
:root {
  --bg-base: #0a0a0f;
  --bg-elevated: #121218;
  --glass-fill: rgba(255, 255, 255, 0.06);
  --glass-border: rgba(255, 255, 255, 0.12);
  --glass-blur: 20px;

  --accent-primary: #8b5cf6;      /* violet */
  --accent-secondary: #ec4899;    /* pink */
  --gradient-primary: linear-gradient(135deg, var(--accent-primary), var(--accent-secondary));

  --text-primary: #f5f5f7;
  --text-secondary: rgba(245, 245, 247, 0.6);

  --radius-lg: 20px;
  --radius-md: 14px;
}

.glass-panel {
  background: var(--glass-fill);
  backdrop-filter: blur(var(--glass-blur));
  -webkit-backdrop-filter: blur(var(--glass-blur));
  border: 1px solid var(--glass-border);
  border-radius: var(--radius-lg);
}
```
- `GlassCard.tsx` wraps `.glass-panel` as a reusable component; every card (song, playlist, settings section) composes it rather than redefining blur/border per component.
- Micro-animations: 150–200ms ease-out on hover/tap scale (`whileTap={{ scale: 0.97 }}` in Framer Motion) for anything tappable — song rows, buttons, nav icons.
- Album-art-driven ambient gradient on `FullScreenPlayer` is a nice-to-have (sample dominant color via a canvas pixel read) — sequence it as a Phase 10 polish item, not core path, since it's easy to get wrong and blocking on it stalls the player itself.

## 10. Build Order Summary (at a glance)

```
Phase 0  → Scaffold
Phase 1  → Firebase (auth + firestore + rules)
Phase 2  → Music API adapters + gateway fallback chain
Phase 3  → Zustand stores (state only, no audio yet)
Phase 4  → Audio engine hook (real playback logic)
Phase 5  → Player UI components
Phase 6  → Page layouts + navigation
Phase 7  → Firestore feature wiring (likes/playlists/history)
Phase 8  → Capacitor + background audio + APK build
Phase 9  → Cache/settings utility
Phase 10 → Polish, animations, resilience testing
```

Each phase should end in a runnable, visibly-working state (`npm run dev` shows real progress) before moving to the next — don't let Antigravity batch multiple phases into one giant diff, since the fallback-chain and background-audio phases in particular need to be debugged in isolation.
